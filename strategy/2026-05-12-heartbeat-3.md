## 1. Diagnosis: what's the actual structural problem?

The autonomy failure is **concurrent dispatch without dependency enforcement**.

The orchestrator fires builders as soon as issues enter `proposed`, with no serial gate. In a monorepo where every UI feature touches `App.tsx`, `channels.ts`, and `ipc-handlers.ts`, two simultaneous builders are nearly guaranteed to conflict. The `depends_on` metadata in issue bodies is decorative — the orchestrator ignores it at dispatch time.

This is not a builder quality problem. Four PRs passed verifier. The code is good. The problem is purely mechanical: branches cut from stale main become unmergeable after any concurrent PR lands.

**The failure has now happened twice in the same session**, which means the prior heartbeat's strategy note (hb2) documented the risk but didn't prevent it — because the orchestrator continued parallel dispatch anyway. The pattern will recur on every wave until Fix 1 (serial gating on `depends_on`) is enforced by the orchestrator itself.

## 3. What to do about the 4 blocked PRs

### Options evaluated

**A. Re-issue as fresh issues that rebase latest main**  
Cost: wastes all prior verifier work; 4 more build cycles; risks the same conflict loop if dispatched concurrently.  
Benefit: clean history.  
**Verdict: NO** — the work is done and verified. Re-issuing is pure waste.

**B. Define `depends_on` convention and let orchestrator enforce serially**  
This is the correct systemic fix but requires orchestrator code change — not in strategist's power.  
**Verdict: RECOMMEND as meta-issue, but can't fix today.**

**C. Make builder rebase before opening PR**  
Partial defense. Reduces but doesn't eliminate the window.  
**Verdict: YES as a builder template update (separate meta-issue).**

**D. Make verifier rebase before merging**  
Requires verifier to attempt rebase+test+push. More complex but fully automatic.  
**Verdict: YES as a meta-issue (longer-term).**

**E. Close conflicting PRs and let next wave start clean**  
Cost: loses 4 PASS'd verified PRs. Future builders start from scratch.  
Benefit: clean state, no human rebase needed, next wave has no conflicts.  
**Verdict: VIABLE but only if operator explicitly chooses. Do not close from strategist.**

**F. Wait for operator rebase (issue #11 human-gate is already open)**  
Issue #11 documents this and requests operator rebase.  
**Verdict: YES — this is the right path. The work is good. Operator rebase is the cheapest resolution.**

### Decision: WAIT + META-ISSUES

- DO NOT close the blocked PRs (operator may rebase them — they passed verifier)
- DO NOT open new feature issues this wave (see Fix 4 in failure note)
- DO open meta-issues for: (1) orchestrator serial gating, (2) builder rebase discipline
- The operator rebase path for #1→#3→#9+#10 in serial order is the optimal resolution
